# Attest Security Assessment

Scope: Week 1 backend/API (registration, JWT authentication, document upload, versioning, verification, local storage, and audit logging). Reviewed 2026-09-02. Sui, Walrus, Seal, and document encryption are intentionally deferred to Week 2.

## Controls verified

- Document ownership is taken from the verified JWT request attributes. `ownerId` form fields are ignored. Owners and admins may access documents; other users receive 403. A brand-new wallet account always resolves to `SIGNER`, so a login request cannot self-assign `ADMIN`.
- Uploads are limited to PDF MIME type, `%PDF-` signature, non-empty content, and 10 MB. Storage names are generated and normalized beneath the configured directory; retrieval rejects references outside it.
- The wallet challenge/verify endpoints are limited to five requests per minute per IP by an in-memory, per-instance filter.
- JWTs use an HMAC signing key, require a valid signature and expiration, and carry the authenticated subject and role. Missing, malformed, tampered, expired, or malformed-claim tokens are rejected.
- Authentication is wallet-native (see "Wallet-native authentication" below) — there is no password to compromise. DB and JWT secrets are configuration values; the JWT secret has no source default. SQL logging is disabled.
- Upload, amendment, and verification events are persisted with document, actor, timestamp, action, and detail. No API exposes audit mutation.
- Generic exceptions return minimal responses without stack traces, paths, class names, library versions, or database details.

## Explicit threat scenarios

- **Old versions / modified files:** each amendment is a new document row and hash; the original row remains unchanged. Verification of a changed valid PDF returns `Integrity verification failed` and records `VERIFY_FAILED`.
- **Unauthorized operations:** the JWT filter establishes identity before controllers run; the service compares that identity with the stored owner or the signed role `ADMIN`.
- **Token reuse:** there is no revocation list or refresh rotation. The one-hour expiry limits exposure, but a stolen token remains valid until expiry. This is a documented later-hardening item.
- **Distributed rate limiting:** the current limiter is intentionally in-memory and safe only for the single-instance Week 1 architecture. Redis or another shared store is required across instances.
- **Alerting:** audit logging is present; automated anomaly detection and paging are deferred.


## Accepted risk: default role for a brand-new wallet account

A wallet address logging in for the first time — which is also how an account
is created, see "Wallet-native authentication" below — receives the global
`SIGNER` role by default (previously `VIEWER`, back when accounts were
email/password). This was a deliberate product decision to reduce onboarding
friction in the team-based model, where team-scoped roles are the primary access
control and the global role is largely secondary.

**What is retained:** the role is assigned server-side in `WalletAuthService`
and never taken from anything the client supplies, so a first-time login cannot
self-escalate to `ADMIN`. The only path to `ADMIN` is the configured bootstrap
address plus the admin-only promotion endpoint.

**Accepted trade-off:** any new wallet account can upload and amend documents in
teams it belongs to without prior admin approval, because global `SIGNER` is in
the document write-role set. In deployments where onboarding should be gated,
the default should be returned to `VIEWER`.



## Wallet-native authentication (supersedes Week 1 password auth)

Email/password login and registration have been fully replaced. There is no
password anywhere in the system, and no endpoint accepts one. Every account is
identified by a Sui address, proven at login time — never claimed.

**Flow:** `POST /api/auth/wallet/challenge` issues a random 24-byte nonce, valid
for `app.sui.challenge-ttl-seconds` (default 5 minutes), embedded in a
human-readable message. The client has a wallet sign that exact message and
posts the signature to `POST /api/auth/wallet/verify` with the nonce and the
claimed address. The nonce is consumed in one atomic conditional `UPDATE`
(`WalletAuthChallengeRepository.consume`) before the signature is even checked,
so a second request racing on the same nonce cannot both pass — one wins the
update, the other sees zero rows affected and is rejected. The account is only
found-or-created *after* the signature verifies.

**Signature verification is scheme-dependent, deliberately:**
- **Ed25519** (standard wallets, e.g. Slush) is verified entirely inside this
  backend: Sui's personal-message intent-wrapping (a 3-byte intent header + a
  BCS-encoded byte vector), BLAKE2b-256, then Ed25519, all reproduced from the
  installed `@mysten/sui` SDK's own source rather than from memory, and
  cross-checked in `SuiSignatureVerifierTests` against a signature that SDK
  itself generated.
- **zkLogin** (Google, via Enoki) is never verified locally. A zkLogin
  signature embeds a Groth16 proof that is only valid against the current
  epoch's OAuth JWKs — correctly checking that is exactly what
  `@mysten/sui`'s own verifier does by calling Sui's official
  `verifyZkLoginSignature` GraphQL query rather than doing it in-process. This
  backend calls that same query directly. An unreachable or erroring endpoint
  throws (`ZkLoginVerificationUnavailableException`, mapped to 503) — it is
  never treated as a successful verification.
- Any other signature scheme is rejected outright
  (`UnsupportedSignatureSchemeException`, 400).

**Bootstrap admin:** `ADMIN_BOOTSTRAP_SUI_ADDRESS` pre-creates a single `ADMIN`
row for a configured address at startup, if that address has no account yet.
This does not grant access on its own — the real owner of that address still
has to prove control of it through the same challenge/verify flow as anyone
else. It only decides which role that first login resolves to.

**Retired along with password auth:** `POST /api/users/me/sui-address` (linking
a wallet to an existing account) has been removed, not just deprecated. It
trusted a client-claimed address with no signature proof at all — safe only
when it was a secondary convenience bolted onto a password-authenticated
account, but a live account-takeover path once addresses became every
account's primary identity (log in with someone's address before they ever do,
and their eventual real login would have found your pre-existing row). Wallet
addresses are now attached to an account in exactly one place:
`WalletAuthService.verifyAndFindOrCreateUser`, immediately after a valid
signature is checked.

**Manual migration required for existing databases:** `User.email` and
`User.passwordHash` are now nullable in the entity (wallet-only accounts have
neither), but `ddl-auto=update` never relaxes an existing `NOT NULL`
constraint on a column that predates this change — it only adds new
tables/columns. Any database created before this migration needs, once:

```sql
ALTER TABLE users ALTER COLUMN email DROP NOT NULL;
ALTER TABLE users ALTER COLUMN password_hash DROP NOT NULL;
```

Without this, every wallet-only sign-in fails with a
`DataIntegrityViolationException` at the moment a new account is created —
the app looks broken, but the actual cause is silent at the API layer since
it surfaces as a generic 500. A brand-new database (dropped and recreated by
Hibernate from scratch) does not need this — the column is only ever created
nullable going forward.

**Known gap:** `test-attest.sh`, the manual curl-based acceptance script, still
calls the removed `/api/auth/login` and `/api/auth/register` endpoints and has
not been updated — it is not part of `./mvnw test` and does not gate anything,
but it no longer runs successfully end-to-end.

## Test evidence

Run `./mvnw test`. The current suite covers context startup, ownership/role controls, upload and integrity checks, JWT tamper rejection, the wallet challenge/verify HTTP flow (issuance, a genuine Ed25519 signature accepted, nonce replay rejected, address mismatch rejected, unknown nonce rejected), the Ed25519 verification core cross-checked against `@mysten/sui`'s own SDK output, and the sixth-request rate-limit boundary. A live PostgreSQL run, a live zkLogin verification against Sui's GraphQL endpoint, and a client-level acceptance test remain deployment checks.
